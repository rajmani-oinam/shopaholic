## 1. Tailwind CSS v4 with Next.js 16

**Decision**: Use Tailwind CSS v4 with CSS-based configuration (`@import "tailwindcss"` + `@theme` directive for custom pastel colors). No `tailwind.config.js` file.

**Rationale**: Tailwind v4 moved to a CSS-first configuration model. Custom theme tokens are declared in the CSS file using `@theme { --color-*: ...; }`. This is simpler, faster, and the default for Next.js 16.

**Installation**:
```bash
npm install tailwindcss @tailwindcss/postcss postcss
```

**Configuration**: Create `postcss.config.mjs` with `@tailwindcss/postcss` plugin. In `global.css`:
```css
@import "tailwindcss";

@theme {
  --color-pastel-bg: #faf5ff;
  --color-pastel-card: #ffffff;
  --color-pastel-purple: #e9d5ff;
  --color-pastel-blue: #dbeafe;
  --color-pastel-green: #d1fae5;
  --color-pastel-amber: #fef3c7;
  --color-pastel-rose: #ffe4e6;
  --color-pastel-text: #1e1b4b;
  --color-pastel-muted: #6b7280;
}
```

**Alternatives considered**: Tailwind v3 config file — rejected because Next.js 16 ships with v4 support and v3 config is legacy.

**Gotchas**:
- Tailwind v4 sets `cursor: default` on buttons by default; add `cursor-pointer` explicitly or override in base layer
- No `tailwind.config.js` — all config is in CSS

## 2. shadcn/ui with Tailwind v4

**Decision**: Use `npx shadcn@latest init` with `new-york` style. Components are copied into `components/ui/`. Needed components: Button, Card, Checkbox, Dialog, AlertDialog, Input, Label.

**Rationale**: shadcn provides accessible, keyboard-navigable, ARIA-compliant primitives built on Radix UI. Source is copied into the project — no runtime npm dependency for shadcn itself.

**Radix dependencies installed**:
- `@radix-ui/react-slot` (Button)
- `@radix-ui/react-dialog` (Dialog)
- `@radix-ui/react-alert-dialog` (AlertDialog)
- `@radix-ui/react-checkbox` (Checkbox)
- `@radix-ui/react-label` (Label)

**Peer dependencies**:
- `clsx` — conditional className composition
- `tailwind-merge` — Tailwind class conflict resolution
- `lucide-react` — icon library
- `tw-animate-css` — animation utilities (replaces deprecated `tailwindcss-animate`)
- `class-variance-authority` — variant management for component styles

**Configuration**: `components.json` is generated by `shadcn init`. Uses `@/components/ui` as the component directory and `@/lib/utils` for the `cn()` helper.

**Alternatives considered**: Building Dialog/AlertDialog/Checkbox from scratch — rejected because accessibility compliance (focus trap, keyboard nav, ARIA attributes, screen reader announcements) would require ~500+ LOC of reimplementation.

**Gotchas**:
- The `default` style is deprecated; use `new-york` only
- shadcn expects a `lib/utils.ts` file with a `cn()` function

## 3. date-fns for Date Arithmetic

**Decision**: Use `date-fns` v4 (latest). Import only the functions needed: `differenceInCalendarDays`, `isBefore`, `format`, `startOfDay`.

**Rationale**: Tree-shakeable (~3–5 kB for the needed functions). Handles calendar-day diffs correctly across DST boundaries. ESM-only, which aligns with Next.js 16's module system.

**Installation**:
```bash
npm install date-fns
```

**Key functions**:
- `differenceInCalendarDays(endDate, today)` → integer days remaining
- `isBefore(endDate, today)` → boolean for overdue check
- `startOfDay(date)` → normalize to midnight for consistent diffs
- `format(date, 'MMM d, yyyy')` → display formatting

**Alternatives considered**:
- Native `Date` math — rejected because calendar-day diffs are error-prone across DST transitions
- `dayjs` — rejected because date-fns is tree-shakeable and doesn't require plugin loading for basic operations
- `Temporal` API — rejected because not yet widely supported in browsers

**Gotchas**:
- date-fns v4 is ESM-only (dropped CJS) — fine for Next.js 16
- Store dates as ISO 8601 strings in localStorage, parse with `new Date()` or `parseISO()` when computing diffs

## 4. localStorage with React 19 + Next.js App Router

**Decision**: Initialize state with a default value (empty array), then hydrate from localStorage in a `useEffect` on mount. All localStorage calls wrapped in try/catch.

**Rationale**: `localStorage` is not available during SSR. Putting `localStorage.getItem()` in a `useState` initializer causes hydration mismatch errors. The `useEffect` approach ensures the server and client render the same initial HTML.

**Pattern**:
```typescript
const [goals, setGoals] = useState<Goal[]>([]);

useEffect(() => {
  try {
    const stored = localStorage.getItem('do-it-goals');
    if (stored) setGoals(JSON.parse(stored));
  } catch { /* ignore corrupt data */ }
}, []);

useEffect(() => {
  try {
    localStorage.setItem('do-it-goals', JSON.stringify(goals));
  } catch { /* ignore quota exceeded */ }
}, [goals]);
```

**Alternatives considered**:
- `useSyncExternalStore` with localStorage — rejected because it adds complexity without benefit for this single-tab use case
- Cookies — rejected because cookie size limit (4 kB) is too small for unbounded goal lists
- IndexedDB — rejected because it's overkill for simple JSON storage at this scale

**Gotchas**:
- First render shows empty state, then goals appear after hydration (brief flash) — acceptable for this scope
- localStorage has a ~5 MB limit per origin

## 5. React Context with Next.js App Router

**Decision**: `GoalProvider` is a `"use client"` component wrapping `{children}` in `layout.tsx`. The root layout stays a Server Component. A custom `useGoals()` hook provides type-safe access with a guard throw.

**Rationale**: React Context requires client-side rendering. The provider pattern with a custom hook is the standard recommended approach for App Router projects.

**Pattern**:
```typescript
// contexts/GoalContext.tsx — "use client"
// Provides: goals, addGoal, completeGoal, deleteGoal
// Internally syncs to localStorage via useEffect

// hooks/useGoals.ts
export function useGoals(): GoalContextValue {
  const ctx = useContext(GoalContext);
  if (!ctx) throw new Error('useGoals must be used within GoalProvider');
  return ctx;
}
```

**Layout integration**:
```tsx
// app/layout.tsx (Server Component)
<GoalProvider>{children}</GoalProvider>
```

**Alternatives considered**:
- Zustand / Jotai — rejected per constitution (state management must use React Context API)
- Props drilling — rejected because multiple components need goal state

**Gotchas**:
- All components consuming context must be Client Components (`"use client"`)
- Wrap mutation functions in `useCallback` to prevent unnecessary re-renders
